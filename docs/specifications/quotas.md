# 仕様書: クォータとレート制限（JSON）

本書は「使いすぎない」ための上限を JSON で宣言する仕様を定義する。クォータは総量、レート制限は瞬間的な頻度を制御する。両者は独立して評価する。

---

## 1. 基本方針

### 1.1 2 種類の制御

| 種別 | 目的 | 単位 | 定義場所 |
|---|---|---|---|
| レート制限 | 短時間の連続アクセスを抑える | ホストあたりの最小間隔 | ネットワークプロファイルの `minIntervalMs` |
| クォータ | 総量（回数・件数・文字数）を抑える | セッション・日次・時間窓 | クォータポリシー（`quotas/<id>.json`） |

### 1.2 ポリシーの参照

設定 `quota` で ID を参照するか、インライン定義を記述する。`--quota <id>` と環境変数 `LLMSEARCH_QUOTA` で一時的に切り替えられる。

### 1.3 上限到達時の振る舞い

上限に達した場合、該当操作を実行せず、次の情報を返す。

1. 超過した項目名（例: `day.searches`）
2. 要求量、現在の消費量／上限、および要求後の見込み消費量（例: `requested 51, used 1/50, projected 52/50`）
3. リセット時刻（次に窓が開く時刻）
4. 解除方法（設定変更・`quota reset`・待機）

暗黙に上限を超えること、自動で上限を緩めることは行わない。

## 2. クォータポリシーの構造

### 2.1 トップレベル

| キー | 必須 | 型 | 内容 |
|---|---|---|---|
| `schemaVersion` | 必須 | 整数 | スキーマ版（初期リリースは `2`） |
| `id` | 必須 | 文字列 | ポリシー ID |
| `description` | 任意 | 文字列 | 説明 |
| `enabled` | 任意 | 真偽値 | 既定 `true`。`false` のとき全項目を無制限とする |
| `session` | 任意 | オブジェクト | セッション単位の上限（§2.2） |
| `day` | 任意 | オブジェクト | 日次（端末のローカル日付）の上限（§2.3） |
| `window` | 任意 | 配列 | 任意の時間窓の上限（§2.4） |
| `total` | 任意 | オブジェクト | 累積の上限（§2.5） |
| `onExceed` | 任意 | 文字列 | `stop`（既定） / `warn` |

### 2.2 計測項目

各単位（`session` / `day` / `window` / `total`）で指定できる項目は次の 4 つである。省略した項目は無制限とする。

| キー | 型 | 内容 |
|---|---|---|
| `searches` | 整数 | 検索リクエストの回数。フォールバックで別エンジンを試した場合は、試した回数だけ数える |
| `fetches` | 整数 | 本文取得（HTML 取得）の回数。robots.txt とリダイレクト、キャッシュからの再出力は数えない |
| `results` | 整数 | 取得した検索結果の件数（フィルタ前） |
| `chars` | 整数 | 出力した本文の文字数（`read` の合計）。取得しただけでは消費しない |

### 2.3 日次の区切り

`day` は端末のローカルタイムゾーンにおける 0 時で区切る。サーバー時刻や UTC では区切らない（利用者の体感と一致させるため）。タイムゾーンは `chrono::Local` を用い、設定で変更しない。

### 2.4 時間窓（`window`）

| キー | 必須 | 型 | 内容 |
|---|---|---|---|
| `minutes` | 必須 | 整数 | 窓の長さ（1〜10080） |
| `searches` ほか | 任意 | 整数 | 窓内の上限 |

窓は「スライディングウィンドウ」ではなく「固定窓」とし、最初の消費時刻から `minutes` 経過でリセットする。判定を単純にし、消費量の説明可能性を保つためである。

### 2.5 累積（`total`）

`total` は状態ディレクトリを作り直すまで減らない累積値である。`quota reset` で明示的に 0 にできる。

### 2.6 `onExceed`

- `stop`: 上限到達時に操作を中止する（既定）。
- `warn`: 上限到達後も操作を許可するが、消費のたびに警告 `W5005`（`quota <項目> is over its limit (continuing)`）を表示する。上限の 2 倍に達した時点で `stop` と同じく `E5005` で停止する（暴走の歯止め）。履歴には専用の印を付けない（`search` などの既存レコードに `quotaExceeded` は含めない）。

## 3. 消費の単位と数え方

### 3.1 消費のタイミング

| 操作 | 消費する項目 | タイミング |
|---|---|---|
| `search` | `searches` に送信回数、`results` に取得件数（フィルタ前）を加算 | 送信成功後 |
| `engines test` | `searches` に送信回数、`results` に取得件数（フィルタ前）を加算。明示 `--session` が無い場合は session スコープを変更せず、日次・窓・累積だけを計上 | 送信成功後 |
| `next` / `refine` | 同上 | 送信成功後 |
| `outline`（未キャッシュ） | `fetches` +1 | 取得成功後 |
| `outline`（キャッシュ済み） | 消費しない | — |
| `read` | `chars` に出力文字数を加算 | 出力後 |
| `history show` | 消費しない（本文の再出力は行わず、メタデータと記録のみを表示する） | — |

`outline` は取得した本文の文字数を `chars` に加算しない。見出し一覧を眺めるだけで本文の予算を消費しないようにするためである。`chars` は `read` で実際に出力した分だけ増える。

### 3.2 失敗時の扱い

- provider page、抽出 retry、HTTP 層の transport retry、fallback / merge の各エンジンを含む、検索で発生する**各 HTTP 送信の直前**に `searches` クォータを判定する。判定には現在の消費量に加え、同一操作中に既に送った要求数も含める。上限を超える次の要求は送信しない。
- 操作全体が失敗した場合（どのエンジンでも結果が得られなかった、ネットワーク障害・タイムアウト、取得の失敗、または途中の送信がクォータで拒否された場合）は `searches` / `fetches` を消費しない（再試行の余地を残すため）。ただし `next` がクォータ超過で送信前に止まった場合は、失敗した操作を `next` 履歴（`added: 0`, `terminationReason: "quota"`）へ記録し、検索ページ状態は変更しない。
- 操作が成功した場合は、その過程で送った回数だけ `searches` を消費する。したがってフォールバックで 2 番目のエンジンを使った場合は 2 回分、同一エンジン内で再送信した場合はその回数分となる。`searches` は「送信した回数」、`results` は「得られた件数」である。
- 明示セッションの無い診断コマンド（例: `engines test`）は新しいセッションを作らず、空の session ID で計上する。この場合、セッション単位の消費量は変更・表示せず、保存済みの別セッションの `session_key` と消費量を保持する。日次・窓・累積の対象となる使用量は通常どおり更新する。
- `robots.txt` の取得、リダイレクトの追従、キャッシュからの再出力は消費しない。

### 3.3 消費の記録

消費は操作の成功直後に永続化する。プロセスが異常終了しても、成功済みの消費は失われない（書き込みは原子的に行う）。逆に、送信前に消費を先取りしない。

## 4. 状態と表示

### 4.1 カウンタの保持

カウンタは状態ディレクトリの `counters.json` に保持する。内容は「窓の開始時刻」「窓内の消費量」「日次・セッション・累積の消費量」である。セッション単位の消費量は `session_key` が示すセッションに属する。セッション ID が空のコマンドは `session_key` や既存のセッション消費量を上書きせず、session スコープの計測・判定・表示を行わない。`quota show` / `quota check` は明示セッションが無い場合に保存済みカウンタが指す有効なセッションを再開し、対象が無ければ session スコープを表示しない。

### 4.2 残量の表示

- すべての検索・取得・読み取りの出力に `quota` を含める。
- 対話モードでは、操作のたびに該当する項目の消費量を `12/50 (session)` の形式で 1 行に添える。
- JSON の各メトリクスは `name`, `used`, `limit`, `remaining`, `resetsAt` を持つ。上限到達時は、要求量・現在量・要求後の見込み量とリセット時刻を表示する。

### 4.3 例

```text
session.searches                12 / 50
day.searches                    340 / 500     2026-11-08T00:00 local
session.fetches                 8 / 100
```

リセット時刻は端末のローカル日付の 0 時を `YYYY-MM-DDT00:00 local` の形式で表す。

### 4.4 コマンド

| コマンド | 内容 |
|---|---|
| `quota show` | 全項目の上限・消費量・残量・リセット時刻を表示する |
| `quota reset [--scope session\|day\|window\|total\|all]` | 指定した範囲の消費量を 0 にする。`--yes` を要求する。既定は `session`。上記以外の語は全消去にせず `E1004` を返し、hint に利用可能な `--scope` 指定を列挙する |
| `quota check --kind search\|fetch\|read --amount <n>` | 消費可能かを判定する（消費はしない）。スクリプトの事前確認用 |

## 5. 既定のポリシー

同梱の `default` ポリシーは次のとおり。利用者設定で上書きできる。

| 単位 | `searches` | `fetches` | `results` | `chars` |
|---|---|---|---|---|
| `session` | 50 | 100 | 500 | 200000 |
| `day` | 500 | 1000 | 5000 | 2000000 |
| `total` | 未設定 | 未設定 | 未設定 | 未設定 |

`window` は既定で 60 分あたり 120 検索を設定する（短期間の連続呼び出しを抑えるため）。利用者設定で外すことも、別の窓を足すこともできる。

---

## 6. 監査

### 6.1 履歴への記録

消費を伴う操作は対応する履歴イベントに記録し、`search` / `next` の結果件数・除外数・エンジン ID は `payload` に含める。`HistoryEntry` は任意の `cost` / `remaining` フィールドも持つが、これらは現在 `quota reset` の監査記録で使用する。`quota reset` はいつ何をリセットしたかを履歴に記録し、少なくとも次を含める。

- 実行日時（`at`、UTC）とセッション識別子
- リセットした範囲（`session` / `day` / `window` / `total` / `all`）
- 適用中のクォータポリシー ID
- リセット前後の消費量（`cost` にリセット前、`remaining` にリセット後）

`quota reset` は消費を伴わないため、`searches` / `fetches` などの計測値を増やさない。履歴の記録に失敗してもリセット自体は成功として扱い、警告を表示する（監査記録の失敗で解除操作を巻き戻さない）。

### 6.2 改変の検出

カウンタファイル（`counters.json`）が JSON として読めない場合、`.corrupt-<timestamp>` へ退避し、0 から再開する。再開は警告なしで行い、履歴へは記録しない（読めなかったファイルは退避先に残るため、事後に確認できる）。同じ扱いをセッション状態の破損にも適用する。

### 6.3 上限の引き上げ

上限の引き上げは設定変更のみで行う。コマンドライン引数 `--quota` で別ポリシーを指定できるが、その場合も履歴に適用ポリシー ID を記録する。
