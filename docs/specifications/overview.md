# 仕様書: 概要（Overview）

本書は `llmsearch` の目的・設計原則・用語・利用シナリオ・スコープ・全体構成を定義する。

---

## 1. 目的と背景

### 1.1 解決したい課題

LLM エージェントに Web 調査をさせると、検索結果ページの HTML や記事全文をそのままコンテキストへ流し込みがちである。これはコンテキストを浪費するだけでなく、ナビゲーションや広告などのノイズ、無関係な記述を大量に混入させ、回答品質を下げる原因になる。

人間は Web 調査の際に段階的な絞り込みを行っている。まず検索結果の一覧（タイトルと概要）を眺め、気になる数件を開き、記事の見出し構成だけを確認し、必要な節だけを読む。本ツールはこの手順をターミナル上に再現し、各段階で「次に何をするか」を利用者（人間または LLM）が選べるようにする。

同時に、検索エンジンは頻繁に仕様・HTML 構造・API 形式を変える。特定エンジンに実装を依存させると、変更のたびにコード修正が必要になる。本ツールは検索エンジンおよびネットワーク挙動をすべて JSON 設定で宣言し、コード変更なしに切り替え・追加できることを必須要件とする。

### 1.2 提供する価値

- **段階的開示**: 一覧（既定 7 件）→ 見出し（既定 h1〜h3）→ 節本文の 3 段階だけを出力する。
- **エンジン非依存**: 検索エンジンの追加・差し替えは JSON のみで行う。実装はエンジン固有の形式を知らない。
- **ネットワークの宣言的制御**: タイムアウト・リトライ・プロキシ・レート・robots.txt の扱いを JSON で指定する。
- **ノイズの抑制**: 結果フィルタ（ドメイン・パターン・重複・件数）と本文フィルタ（不要要素・短小節）を JSON で指定する。
- **使いすぎの防止**: 検索回数・取得回数・読み取り量に上限（クォータ）を設定できる。
- **再現性**: 取得した Markdown と閲覧履歴をローカルに保存し、後から同じ節を引き直せる。

### 1.3 想定利用者

| 利用者 | 利用形態 | 重視する点 |
|---|---|---|
| LLM エージェント | ツール呼び出しとして 1 操作ずつ実行 | 出力の小ささ、JSON の安定性、失敗時の回復手段、上限の予測可能性 |
| 開発者・研究者 | ターミナルで対話的に実行 | 操作の分かりやすさ、履歴の参照、エンジン切替の容易さ |
| 自動化スクリプト | 非対話サブコマンドの連結 | 終了コード、決定論的な出力、クォータによる暴走防止 |
| 運用者 | 設定ファイルの管理 | エンジン定義の検証、フィルタの調整、監査可能な履歴 |

## 2. 設計原則

### 2.1 段階的開示（Progressive Disclosure）

各段階の出力は、次の判断に必要な最小限の情報に限定する。検索段階では本文を出さず、アウトライン段階では節本文を出さない。

### 2.2 コンテキスト予算の明示

出力の文字数を常に計測して表示し、上限を超える場合は行境界で切り詰めたうえで「切り詰めた」ことを明示する。暗黙の大量出力を行わない。

### 2.3 探索と取得の分離

検索（一覧の取得）と文書取得（HTML の取得と変換）は別操作とする。検索結果を選ばない限り、外部へ追加のリクエストを送らない。

### 2.4 エンジン非依存（宣言的定義）

検索エンジンは「リクエストの組み立て方」と「応答からの取り出し方」を JSON で宣言したものとして扱う。コアは宣言を評価するだけで、エンジン名による分岐を持たない。したがって新しいエンジンの追加はファイル追加のみで完結し、プログラムの再ビルドを要さない。

### 2.5 宣言的設定による挙動の外部化

ネットワーク挙動（タイムアウト・リトライ・プロキシ・同時実行・レート）、フィルタ、クォータも JSON で指定する。設定は「既定値 → 利用者設定 → プロファイル → 環境変数 → コマンドライン」の順で解決し、由来を機械的に説明できるようにする。

### 2.6 決定論的な出力

同一の入力（同じクエリ・同じエンジン定義・同じキャッシュ済み文書）に対しては、同一の出力を返す。並び順・番号・抽出規則は固定であり、実行のたびに変化しない。

### 2.7 ローカル完結とプライバシー

履歴・キャッシュ・設定はローカルディスクのみに保存する。テレメトリや外部への利用状況送信は行わない。認証情報は設定ファイルへ直接記述せず、環境変数名の参照として扱う。

### 2.8 礼儀と抑制

公開 Web へのアクセスは、robots.txt の尊重、ホスト単位のレート制限、識別可能な User-Agent の付与、総量のクォータを既定動作とする。上限に達した場合は暗黙に継続せず、理由と解除方法を明示して停止する。

## 3. 用語

| 用語 | 定義 |
|---|---|
| セッション | 1 回の起動から終了まで、または `--session` で継続される一連の操作単位。識別子は `YYYYMMDD-HHmmss-xxxx` 形式 |
| 検索結果 | エンジン定義に従って抽出・正規化された 1 件の結果。セッション内で `R1`, `R2`, … の識別子を持つ |
| ページ | 検索結果の集合のうち、一度に表示する区切り。既定は 7 件 |
| 文書 | 取得して Markdown 化した 1 つの Web ページ。セッション内で `D1`, `D2`, … の識別子を持つ |
| 見出し | Markdown 化された文書中の `#`〜`######` の行。レベルと本文テキストを持つ |
| アウトライン | 文書の見出しの一覧。既定では h1〜h3 のみを表示する |
| 節 | ある見出しから、同レベル以下の次の見出しの直前までの本文範囲 |
| スニペット | 検索結果に付随する短い概要文。既定 120 文字で切り詰める |
| コンテキスト予算 | 1 回の出力に含める最大文字数 |
| エンジン定義 | 検索エンジン 1 つを表す JSON。リクエスト定義と応答抽出定義を持つ |
| エンジンプロファイル | 同一エンジンに対する複数の定義（API 版・HTML 版など）を束ねた単位 |
| 抽出ルール | 応答からタイトル・URL・スニペット等を取り出す宣言（CSS セレクタまたは JSON パス） |
| ネットワークプロファイル | タイムアウト・プロキシ・リトライ等を束ねた名前付き設定 |
| フィルタ | 結果または本文から不要な要素を除外する宣言的規則 |
| クォータ | セッション・日次・時間窓あたりの回数・量の上限 |
| カウンタ | クォータの消費量を記録する永続化された数値 |
| 状態ディレクトリ | 設定・履歴・キャッシュ・カウンタを保存するローカルのディレクトリ |
| 対話モード | 番号入力のメニューで操作する起動モード |
| 非対話モード | 引数で 1 操作を実行して終了するモード |

## 4. 利用シナリオ

### 4.1 対話モードでの調査

利用者は `llmsearch` を引数なしで起動し、検索語を入力する。7 件の結果（番号・タイトル・URL・スニペット）が表示され、メニューから「2. 検索結果の選択」を選ぶ。選択した記事の見出し構成（h1〜h3）だけが表示され、読む節を選ぶとその節の Markdown だけが出力される。調査を終えると履歴に一連の操作が残る。

### 4.2 エージェントからの 1 回呼び出し

エージェントは検索、アウトライン取得、節読み取りをそれぞれ独立したコマンドとして実行し、JSON 出力を解釈して次の操作を決める。状態はセッション識別子を通じてプロセスをまたいで引き継がれる。クォータ残量は各コマンドの出力に含まれ、エージェントは残量から計画を調整できる。

### 4.3 過去の閲覧の再参照

利用者は履歴を一覧表示し、過去に読んだ節を同じ識別子で再出力できる。キャッシュが有効な間は外部へ再取得を行わない。

### 4.4 エンジンの切り替えと検証

利用者はエンジン定義ファイルを追加し、`engines validate` で構文と抽出規則の妥当性を確認したうえで、`--engine <id>` または設定の既定エンジンとして選択する。抽出結果が空の場合は `engines test <id> --query` で 1 回だけ試行し、セレクタを修正する。プログラムの再ビルドは行わない。

## 5. スコープと非目標

### 5.1 初期リリースのスコープ

1. 宣言的エンジン定義（HTML 抽出と JSON 抽出の双方）と、その検証・試行コマンド
2. 複数エンジンの選択・フォールバック・結果のマージ
3. 検索結果のページングと検索語の修正
4. HTML の取得、本文抽出、Markdown 変換（見出し・リスト・表・コードブロックを保持）
5. 見出しアウトラインの表示（深さ既定 3、2〜4 に変更可能）
6. 節単位の抽出とコンテキスト予算に基づく切り詰め
7. 結果フィルタ・本文フィルタ（いずれも JSON 宣言）
8. クォータ（検索回数・取得回数・読み取り量）とレート制限
9. ネットワークプロファイル（タイムアウト・リトライ・プロキシ・UA・robots.txt）
10. 履歴の記録・一覧・検索・再出力・削除
11. 対話モードと非対話モード、テキスト出力と JSON 出力

### 5.2 非目標

- ページ内容の要約・回答生成（本ツールは素材の提供に限定する）
- JavaScript 実行を伴うページの完全な描画（初期リリースでは検出して警告する）
- サイト内の複数ページ巡回、サイトマップ探索、クローリング
- 認証・Cookie・ペイウォールを伴うページの取得（API キー以外の認証は非対応）
- 検索エンジン側の非公開 API の探索や、利用規約に反する自動化
- 複数利用者での共有、サーバー常駐、リモート API としての提供

### 5.3 将来拡張の候補

ヘッドレスブラウザによる描画、MCP サーバーとしての提供、節の要約、複数文書の横断比較、PDF の取り込み、エンジン定義の共有レジストリ。いずれも初期リリースの仕様には含めない。

## 6. 全体アーキテクチャ

### 6.1 パイプライン

1. 設定（JSON）を解決し、エンジン定義・ネットワークプロファイル・フィルタ・クォータを読み込む
2. クォータの残量を確認し、不足していれば理由を返して停止する
3. 選択されたエンジン定義に従ってリクエストを組み立て、送信する
4. 抽出ルールに従って応答から結果を取り出し、正規化・重複除去・フィルタを適用する
5. 結果一覧を `R1` 以降の識別子を付けて表示し、利用者の選択に応じて分岐する
6. 選択された結果の HTML を取得し、本文抽出を経て Markdown へ変換して文書として保存する
7. Markdown から見出しを抽出し、アウトラインを表示する
8. 選択された節の本文だけをコンテキスト予算の範囲で出力する
9. すべての操作を履歴とカウンタへ反映する

### 6.2 設定駆動の境界

コアが知ってよいのは「エンジン定義のスキーマ」「抽出ルールの評価」「フィルタの適用順序」までである。エンジン名・ドメイン名・HTML 構造に依存する知識はすべて JSON 側に置く。この境界を破るコード（例: 特定ホスト名による分岐）は受け入れない。

### 6.3 状態の保持単位

セッション（クエリ・結果一覧・文書・選択状態）、文書キャッシュ（URL と Markdown の対応）、履歴（操作の時系列）、カウンタ（クォータ消費量）の 4 つを状態ディレクトリに保持する。状態はプロセス終了後も再利用できる。

### 6.4 拡張点

1. **エンジン追加**: JSON ファイルの追加のみ。抽出方式（HTML / JSON）はルールで表現する。
2. **抽出方式の追加**: 応答種別ごとの抽出器を追加できる構造とし、既存の抽出器に影響を与えない。
3. **ネットワーク実装の差し替え**: HTTP クライアントを境界として分離し、テストでは偽実装に差し替える。
4. **出力形式の追加**: テキストと JSON の出力形式を対等に扱い、将来の形式追加を容易にする。
5. **未知設定の温存**: 設定ファイルの未知キーを保持し、後方互換性を損なわない。
