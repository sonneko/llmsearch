# 仕様書: 検索とページング

本書はエンジン定義（別冊）を用いた検索実行、結果の正規化、ページング、検索語の修正を定義する。

---

## 1. 検索の実行

### 1.1 エンジンの選択順

1. コマンドラインの `--engine <id[@variant]>`
2. 環境変数 `LLMSEARCH_ENGINE`
3. 設定の `search.engine`
4. 認証情報が不要な有効エンジンのうち定義順の先頭（同梱定義では `duckduckgo`）。該当が無ければ有効エンジンの先頭

上位が優先される。選択されたエンジンが利用不能（`enabled=false`、認証情報の不足、定義の不備）な場合、暗黙に別エンジンへ切り替えず `E4002` を返し、利用可能なエンジン ID を列挙する。

### 1.2 フォールバックとマージ

`search.fallback` が設定されている場合に限り、結果 0 件・拒否（`E4001` / `E4003`）・応答抽出規則の不一致（`E4004`）で次のエンジンを試す。`search.merge` が `true` の場合は `search.engines` に列挙した複数エンジンの結果をラウンドロビンで統合する（フォールバックではなく全エンジンへ送信する）。`search.merge` と `search.fallback` が同時に設定された場合は `search.merge` を優先する。挙動の詳細はエンジン定義の仕様に従う。

### 1.3 送信の制約

検索要求は逐次送信し、並列化しない。通常は 1 論理ページにつき選択エンジンへ要求するが、`page` 方式で `paging.pageSize` と `search.limit` が異なる場合は必要な隣接プロバイダページを複数取得する。抽出結果が空の場合はネットワークプロファイルの retry 設定に従って再送する。フォールバックは候補エンジンを順に試し、マージは `search.engines` の各エンジンを試す。各プロバイダページ、抽出 retry、および HTTP 層の transport retry を含む**各検索 HTTP 送信の直前**にクォータを確認する。レート間隔は各送信に適用し、クォータ不足時はその要求を送信せず `E5005` を返す。

## 2. 結果の正規化

### 2.1 フィールド

| フィールド | 必須 | 内容 |
|---|---|---|
| `id` | 必須 | セッション内の識別子 `R1`, `R2`, … |
| `rank` | 必須 | 表示順（1 始まり）。マージ時は統合後の順位 |
| `title` | 必須 | タイトル。空白を正規化し、既定 100 文字で切り詰める |
| `url` | 必須 | 正規化済みの URL |
| `snippet` | 任意 | 概要文。既定 120 文字で切り詰める |
| `site` | 任意 | 表示用のホスト名（`www.` を除く） |
| `published` | 任意 | 公開日（`YYYY-MM-DD`） |
| `engine` | 必須 | 由来エンジンの `id`（マージ・フォールバック時の識別用） |

### 2.2 URL の正規化

- スキームを小文字化し、ホスト名を小文字化する。既定ポート（80/443）を除去する。
- 追跡パラメータを除去する。対象は `utm_source` / `utm_medium` / `utm_campaign` / `utm_term` / `utm_content` / `utm_id` / `fbclid` / `gclid` / `yclid` / `msclkid` / `mc_cid` / `mc_eid` / `igshid` で固定である（設定キーは持たない）。
- フラグメントは保持する（同一ページ内の見出し参照を壊さないため）。ただし重複判定ではフラグメントを無視する。
- 相対 URL はエンジン定義の `absolutize` 変換で絶対化済みであることを前提とし、未解決の相対 URL を含む結果は破棄する。

### 2.3 重複の除去

正規化 URL（フラグメントを除く）が同一の結果は初出のみを残す。除去後に `id` を連番で振り直し、欠番を作らない。

### 2.4 並び順

エンジン定義が返した順序（`items` の順）を維持する。フィルタによる除外では相対順序を変えないが、フィルタ集合で `diversity: true` が指定された場合はホスト単位に交互配置する。

## 3. ページング

### 3.1 ページサイズ

既定は 1 ページ 7 件。`search.limit` または `--limit` は 1〜30 の整数とし、`--limit` が範囲外なら `E1004` で送信前に拒否する（丸めない）。`limits.maxPageSize`（既定 10）は 1 回のプロバイダ要求の件数上限である。`offset` 方式は 1 回の要求で上限まで取得する。`page` 方式では `paging.pageSize`（`maxPageSize` 以下）をプロバイダのページ幅として、利用者向けの 1 ページを埋めるために必要な隣接ページを取得し、表示範囲を切り出すことがある。

### 3.2 次ページの取得

`next` および `search --page` は、同一クエリ・同一エンジン（マージ時は同一のエンジン集合）で次の論理ページを取得する。`next` / `refine` はグローバル `--engine`（または `LLMSEARCH_ENGINE`）が明示されていなければ、セッションの `lastEngine` を継承する。`offset` 方式で表示件数がエンジンのネイティブページ幅より小さい場合、表示しない結果を飛ばさないよう開始位置の増分に表示件数を使う。それ以外は `offsetStep`（省略時はネイティブページ幅）に従う。`page` 方式では必要なプロバイダページを読み、論理ページの開始位置から表示件数を切り出す。

取得済みの結果は保持し、ページ内表示とセッションに保存する識別子 `R<n>` は一致させ、次ページも連番を継続する。`search --page` の番号は 1 始まりで、指定可能範囲は有効な累積上限と論理ページの開始位置増分から決める。`page` 方式とマージは `search.limit` を使い、`offset` 方式は `limits.maxPageSize` を反映した要求件数と `offsetStep` から実際の増分を使う。ページング非対応のエンジンでは 1 ページ目だけを許可する。

### 3.3 取得上限と終端

累積取得数は `limits.maxResults` / `paging.maxResults` と `search.max_results` のうち小さい上限を超えない。プロバイダが要求数より短いページ、または空のページを返した場合は終端とする。ページング非対応、上限到達、フィルタ適用後に結果が残らない場合も追加取得を案内しない。`next` の JSON イベントと履歴には `terminationReason`（`pagingUnsupported` / `maxResults` / `filtered` / `emptyPage`）を記録する。

次ページの送信前にクォータを判定する。クォータ超過時は送信せず `E5005` を返し、ページ状態は進めないが、`next` 履歴に `terminationReason: "quota"`、`added: 0` を記録する。空ページはエラーとしない。

### 3.4 失敗時の扱い

次ページ取得に失敗した場合、表示済みの一覧を破棄しない。エラーを標準エラーへ表示し、メニューへ戻る。ページ位置は進めない。

## 4. 検索語の修正

### 4.1 挙動

「検索ワードを修正する」操作は、現在の検索語を初期値として提示し、編集後の文字列で新しい検索を実行する。`refine` は直前の検索語を `previousQuery` として返し、履歴に `refine` を残す。結果一覧はセッションの `results` を置き換える（別スロット保存は未実装。`plans.md` §7）。

### 4.2 検索語の履歴

セッション内の検索語は出現順に保持し、`next` の対象（直前のクエリ）として使う。`!1` 形式での再利用は未実装（`plans.md` §7）。空文字・空白のみの入力は受け付けない。

### 4.3 入力の正規化

前後の空白を除去し、連続する空白（全角空白を含む）を 1 つにまとめる。制御文字を除去する。最大長は 512 文字とし、超過分は切り捨てて警告 `W1003` を出す。

## 5. 礼儀とレート

### 5.1 ホスト単位の制限

同一ホストへの連続リクエストは、ネットワークプロファイルの `minIntervalMs`（既定 1000）以上を空ける。待機が発生した場合は `W2001` として待機時間を表示する。

### 5.2 同時実行

1 回の操作で同時に取得する文書は `network.maxConcurrency`（既定 2）までとする。この値は HTTP クライアントの接続プール（`pool_max_idle_per_host`）に渡すのみで、並列取得の制御には使っていない。検索リクエストの並列送信は行わない。

### 5.3 robots.txt

本文取得の前に、対象ホストの robots.txt を取得して判定する。設定 `network.robots.respect` が `false` の場合を除き、`Disallow` に該当するパスは取得しない。robots.txt を取得できない場合（404・タイムアウト）は取得を許可する。判定結果は状態ディレクトリの `cache/robots.json` に保持し、`network.robots.ttlMinutes` の間は再利用する。

### 5.4 User-Agent

既定は `llmsearch/<version> (+<repository-url>)` とし、識別可能な文字列とする。ネットワークプロファイルの `userAgent` で変更できるが、空文字は許可しない。

### 5.5 クォータとの関係

レート制限は「短時間の連続アクセスを抑える」ため、クォータは「総量を制限する」ための独立した仕組みである。レート間隔が不足する場合は `minIntervalMs` まで待機してから送信し、クォータ上限を超える場合は送信せず `E5005` を返す。
