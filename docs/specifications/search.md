# 仕様書: 検索とページング

本書はエンジン定義（別冊）を用いた検索実行、結果の正規化、ページング、検索語の修正を定義する。

---

## 1. 検索の実行

### 1.1 エンジンの選択順

1. コマンドラインの `--engine <id[@variant]>`
2. 環境変数 `LLMSEARCH_ENGINE`
3. 利用者設定の `search.engine`
4. プロファイルの `search.engine`
5. 既定エンジン（設定 `search.default_engine`、既定値は同梱の `duckduckgo`）

上位が優先される。選択されたエンジンが利用不能（`enabled=false`、認証情報の不足、定義の不備）な場合、暗黙に別エンジンへ切り替えず `E4002` を返し、利用可能なエンジン ID を列挙する。

### 1.2 フォールバックとマージ

`search.fallback` が設定されている場合に限り、結果 0 件または制限（`E4001` / `E4003`）で次のエンジンを試す。`search.merge` が `true` の場合は複数エンジンの結果を統合する。挙動の詳細はエンジン定義の仕様に従う。

### 1.3 送信の制約

検索リクエストは 1 操作につき 1 エンジン 1 回（フォールバック時は最大で配列長回）とする。並列送信は行わない。リクエスト前にクォータとレート制限を確認し、不足時は送信せずにエラーを返す。

## 2. 結果の正規化

### 2.1 フィールド

| フィールド | 必須 | 内容 |
|---|---|---|
| `id` | 必須 | セッション内の識別子 `R1`, `R2`, … |
| `rank` | 必須 | 表示順（1 始まり）。マージ時は統合後の順位 |
| `title` | 必須 | タイトル。空白を正規化し、既定 100 文字で切り詰める |
| `url` | 必須 | 正規化済みの URL |
| `snippet` | 任意 | 概要文。既定 120 文字で切り詰める |
| `site` | 任意 | 表示用のホスト名（`www.` を除く） |
| `published` | 任意 | 公開日（`YYYY-MM-DD`） |
| `engine` | 必須 | 由来エンジンの `id`（マージ・フォールバック時の識別用） |

### 2.2 URL の正規化

- スキームを小文字化し、ホスト名を小文字化する。既定ポート（80/443）を除去する。
- 追跡パラメータを除去する。対象は設定 `filter.tracking_params` に従い、既定は `utm_*`, `fbclid`, `gclid`, `yclid`, `msclkid`, `mc_cid`, `mc_eid`, `igshid` である。
- フラグメントは保持する（同一ページ内の見出し参照を壊さないため）。ただし重複判定ではフラグメントを無視する。
- 相対 URL はエンジン定義の `absolutize` 変換で絶対化済みであることを前提とし、未解決の相対 URL を含む結果は破棄する。

### 2.3 重複の除去

正規化 URL（フラグメントを除く）が同一の結果は初出のみを残す。除去後に `id` を連番で振り直し、欠番を作らない。

### 2.4 並び順

エンジン定義が返した順序（`items` の順）を維持する。フィルタ適用後も相対順序を変えない。

## 3. ページング

### 3.1 ページサイズ

既定は 1 ページ 7 件。`search.limit` または `--limit` で 1〜30 の範囲で変更する。ただしエンジン定義の `limits.maxPageSize`（既定 10）を超える件数を要求しない。要求件数が上限を超える場合、上限まで分割して取得する。

### 3.2 次ページの取得

「8 件目以降を見る」操作は、同一クエリ・同一エンジン・同一ページング方式で次の位置から取得する。取得済みの結果はそのまま保持し、追加分に連番を継続する。ページ位置の管理はエンジン定義の `paging.style`（`offset` / `page`）に従い、コアは開始位置の数値のみを扱う。

### 3.3 取得上限と終端

次のいずれかに達したら終端とする。

1. `limits.maxResults` または `search.max_results`
2. クォータ（セッションまたは日次の検索回数・取得件数）の残量
3. エンジンが空の結果を返した
4. フィルタ適用後に新規の結果が 1 件も残らなかった

終端では「これ以上の結果はありません」と理由を表示する。空ページはエラーとしない。

### 3.4 失敗時の扱い

次ページ取得に失敗した場合、表示済みの一覧を破棄しない。エラーを標準エラーへ表示し、メニューへ戻る。ページ位置は進めない。

## 4. 検索語の修正

### 4.1 挙動

「検索ワードを修正する」操作は、現在の検索語を初期値として提示し、編集後の文字列で新しい検索を実行する。直前の結果一覧はセッション内の別スロットとして保持し、履歴から参照できる。

### 4.2 検索語の履歴

セッション内の検索語は出現順に保持し、`!1`, `!2` の形式で再利用できる。空文字・空白のみの入力は受け付けない。

### 4.3 入力の正規化

前後の空白を除去し、連続する空白（全角空白を含む）を 1 つにまとめる。制御文字を除去する。最大長は 512 文字とし、超過分は切り捨てて警告 `W1003` を出す。

---

## 5. 礼儀とレート

### 5.1 ホスト単位の制限

同一ホストへの連続リクエストは、ネットワークプロファイルの `minIntervalMs`（既定 1000）以上を空ける。待機が発生した場合は `W2001` として待機時間を表示する。

### 5.2 同時実行

1 回の操作で同時に取得する文書は設定 `network.maxConcurrency`（既定 2）までとする。検索リクエストの並列送信は行わない。

### 5.3 robots.txt

本文取得の前に、対象ホストの robots.txt を取得して判定する。設定 `network.respectRobots` が `false` の場合を除き、`Disallow` に該当するパスは取得しない。robots.txt を取得できない場合（404・タイムアウト）は取得を許可する。判定結果はセッション中キャッシュする。

### 5.4 User-Agent

既定は `llmsearch/<version> (+<repository-url>)` とし、識別可能な文字列とする。ネットワークプロファイルの `userAgent` で変更できるが、空文字は許可しない。

### 5.5 クォータとの関係

レート制限は「短時間の連続アクセスを抑える」ためのものであり、クォータは「総量を制限する」ためのものである。両者は独立に判定し、どちらか一方でも超過していれば送信しない。
